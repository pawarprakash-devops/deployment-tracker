# Redesign API Spec: Pipeline, Ticket, Me, Webhook Enrichment

**Status:** design only, no app code changed. **Implements:** `docs/REDESIGN-PROPOSAL-ROLE-BASED-UX.md` section 8.
**Stack facts verified in this repo:** Next.js 16.3.3 (App Router), `pg` pool (`lib/db.ts`), Jira Cloud REST via `lib/jira.ts`, no test runner installed (`package.json` has only `build`/`lint`). All example data below is synthetic.

## 0. Conventions and shared building blocks

### 0.1 Next 16 route-handler conventions (checked in `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md`)

- `params` is a **Promise**; always `await` it. Signature for the dynamic route:

  ```ts
  // app/api/tickets/[key]/route.ts
  import type { NextRequest } from 'next/server';
  export const dynamic = 'force-dynamic';
  export const maxDuration = 30;
  export async function GET(request: NextRequest, ctx: RouteContext<'/api/tickets/[key]'>) {
    const { key } = await ctx.params;
  ```

  `RouteContext` is a global helper generated by `next dev` / `next build` / `next typegen`. The existing `app/api/deployments/[id]/route.ts` uses the inline form `{ params }: { params: Promise<{ id: string }> }`; either is valid. Prefer the inline form until `typegen` runs in CI.
- GET handlers are **not cached by default** in Next 16; existing routes still declare `export const dynamic = 'force-dynamic'` and set `Cache-Control` explicitly. Do the same. Do not enable Cache Components (`next.config.ts` is empty) for this work.
- `middleware.ts` is **deprecated in Next 16 in favour of `proxy.ts`** (same behaviour, rename only; codemod `npx @next/codemod@canary middleware-to-proxy .`). It still works, so do not rename inside this change. Relevant behaviour: matcher is `/api/:path*` and **every GET passes through unauthenticated**, so all new GET routes must enforce auth inside the handler (the same way `isAdminRequest` is called in `/api/jira/*`).
- `maxDuration = 30` on any route that fans out to Jira (matches `insights`, `stats`, `search`).
- Error body shape stays `{ error: string, ... }`; Jira-config responses keep `{ configured: false }` with HTTP 200 (existing contract).

### 0.2 New shared code (additive, no behaviour change to existing routes)

| New | Where | Purpose |
|-----|-------|---------|
| `getSession(request)` -> `{ role: 'anonymous'\|'viewer'\|'admin', email: string\|null, jiraAccountId: string\|null, authMode }` | `lib/auth.ts` (next to `isAdminRequest`) | Single place for identity. Today returns `admin` iff `isAdminRequest`, else `anonymous`. Option A (SSO) later fills `viewer`/`email`. |
| `canReadJira(session)` | `lib/auth.ts` | **The one-line access switch.** Today `session.role === 'admin'`; under Option A `session.role !== 'anonymous'`. All new Jira-bearing routes call this, never `isAdminRequest` directly. |
| `loadDeployWindow(pool, {limit, statuses, sinceDays})` | `lib/jira.ts` or new `lib/pipeline.ts` | Returns raw deployment rows; `ticketDeploys` is refactored to call it (same output). |
| `deploymentKeys(row)` | `lib/pipeline.ts` | `row.jira_keys` (if column exists) UNION `extractJiraKeys(notes, branch, version, frontend_branch, backend_branch, ticket_link)`. Union, never replace, so legacy rows keep working. |
| `envMeta(name)` -> `{ column, rank, isProduction }` | `lib/pipeline.ts` | Maps free-text env names to board columns and a pipeline rank (table in 1.4). |
| `jiraIssuesByKeysCached(keys, clause?)` | `lib/jira.ts` | Per-key memo (ttl 120 s) on top of the existing `cached()`, chunks of 100 keys, honours the existing 6-in-flight limiter. Fixes the silent 100-key truncation in `jiraIssuesByKeys` (see 1.7). |
| `assigneeId` field on `JiraIssue` | `lib/jira.ts` `toIssue` | `f.assignee?.accountId`, already in the fetched `assignee` field, zero extra Jira cost. Needed for "my work". |

### 0.3 Caching policy (consistent with existing routes)

| Route class | Existing precedent | Applied to |
|-------------|--------------------|-----------|
| Jira-derived, per-viewer-authorised | `Cache-Control: private, max-age=60..300` + in-process `cached(key, ttl, fresh)` + `?fresh=1` bypass | `/api/pipeline` (60 s), `/api/tickets/[key]` (60 s), same TTLs as `/api/jira/deployed` and `/api/jira/issues` |
| DB-only, public read | sha1 `ETag` + `If-None-Match` -> 304, `public, s-maxage=30..60, stale-while-revalidate` | Not used: new payloads contain Jira titles/assignees, so they must never be CDN-shared. |
| Identity | none | `/api/me`: `private, no-store` |

New routes **add `ETag` on top of `private, max-age`** (compute sha1 of the JSON like `/api/deployments` and `/api/health` do). The 90 s UI poll then costs a 304 when nothing changed. `private` + ETag is valid; Vercel's CDN will not store it.

### 0.4 Test strategy shared by all endpoints

No runner exists. Add **Vitest** (node environment) as the only new dev dependency and a `test` script. Route tests call the exported handler directly with `new NextRequest('http://t/api/...', { headers: { cookie: 'tracker_session=...' } })`, `vi.mock('@/lib/db')` for `pool.query`, and `vi.stubGlobal('fetch', ...)` for Jira/GitHub. Put pure logic (placement, journey, key union, env mapping) in `lib/pipeline.ts` so most coverage is plain unit tests with no mocks. Fixtures: a `fixtures/deployments.ts` of synthetic rows.

## 1. `GET /api/pipeline`

Tickets grouped by environment, one call for the Pipeline board and for the Release/Dev/QA lens homes.

### 1.1 Request

`GET /api/pipeline`

| Param | Type / default | Meaning |
|-------|----------------|---------|
| `env` | csv of column ids, default all | Restrict columns (`preview,demo,qa,stage,preprod,prod-ankura,prod-neotia,other`). |
| `view` | `furthest` (default) \| `all` | `furthest`: each ticket appears once, in the furthest column it reached. `all`: a ticket appears in every column where it is currently deployed (used by QA "ready to test per env"). |
| `assignee` | Atlassian accountId, csv, `unassigned`, or **`me`** | Reuses `filterJql` semantics. `me` resolves from `getSession().jiraAccountId`. |
| `status`, `type`, `priority`, `label`, `component`, `version` | as in `filterJql` (quoted + validated) | Applied **in Jira** as a JQL clause on the key set (see 1.5), never in JS. |
| `stage` | one of `STAGES` from `lib/jira.ts` | Post-filter on `stageOf(status)`; computed in JS (no JQL equivalent). |
| `sinceDays` | int 1-90, default 30 | Hide tickets whose latest deploy is older. |
| `limit` | int 1-300, default 150 | Max tickets returned (newest deploy first). `truncated: true` if cut. |
| `fresh` | `1` | Bypass the in-process cache (the Refresh button, as in `insights`). |

Unknown params are ignored. Bad enum values return 400.

### 1.5 SQL / JQL

Two DB queries run in parallel with the Jira calls that depend on them:

```sql
-- A. "where is it" window: identical semantics to ticketDeploys (Success only, newest 300)
SELECT id, environment, status, deployment_type, branch, version,
       frontend_branch, backend_branch, frontend_version, backend_version,
       deployed_by, ticket_link, notes, started_at, completed_at
FROM deployments
WHERE status = 'Success'
ORDER BY started_at DESC
LIMIT 300;

-- B. "what went wrong or is running" overlay: non-success rows for the same horizon
SELECT id, environment, status, deployment_type, started_at, notes, branch,
       frontend_branch, backend_branch, ticket_link
FROM deployments
WHERE status <> 'Success'
  AND started_at >= NOW() - ($1::int * INTERVAL '1 day')      -- sinceDays
  AND (deployed_by IS NULL OR deployed_by NOT LIKE '%Deployment Tracker%')
ORDER BY started_at DESC
LIMIT 300;
```

State derivation per (ticket, env), rows merged newest first: the newest row decides. `Success` or `Rerun - Success` -> `deployed`; `In Progress` -> `in_progress`; `Failed`/`Rerun - Failed` -> `failed` (only if newer than the last success, otherwise ignore); `Rolled Back` -> `rolled_back`. Treat any status matching `/(^|\s)success$/i` as success, as `lib/alerts.ts` does.

> Known gap in the existing code: `ticketDeploys` filters `status = 'Success'` exactly, so reruns recorded by the webhook as `'Rerun - Success'` never count as a deploy. The shared `loadDeployWindow` must use `status ~* '(^|\\s)success$'` for the success window. This is a behaviour improvement to `/api/jira/deployed` and the ready-to-ship queue; call it out in the PR.

Jira (one POST per 100 keys, `/rest/api/3/search/jql`, via `jiraSearch`):

```
key in (VID-1234, VID-1250, ...)  [AND <filterJql clause>]
```

Status/stuck are derived in JS from the returned issues; `stage` filter is JS-side.

`canReadJira(getSession(request))` else **401** `{ error: 'Admin login required' }` (keep the exact string so the existing UI handling works; change to "Login required" only when Option A lands). Without Jira configured the route still works from DB data (tickets carry only `key`), returning `configured: false` with HTTP 200.

### 1.7 Errors

| Case | Status | Body |
|------|--------|------|
| Not authorised | 401 | `{ error: 'Admin login required' }` |
| `assignee=me` but session has no `jiraAccountId` | 400 | `{ error: 'Cannot resolve "me"', code: 'ME_UNRESOLVED' }` |
| Invalid `env`/`view`/`stage`/`sinceDays` | 400 | `{ error, field }` |
| `JIRA_PROJECT_KEYS` unset | 200 degrade | `jiraError: 'Set JIRA_PROJECT_KEYS'`, DB-only board |
| Jira 4xx/5xx/429 after one retry | 200 degrade | `jiraError: <message>`, tickets without Jira fields (same pattern as `/api/jira/deployed`) |
| DB failure | 500 | `{ error }` (log server-side) |

Jira failure must **not** fail the board: the deployment half is the unique value of this endpoint.

### 1.8 Performance notes

- **300-deployment window.** At roughly 8 to 15 deploys per day across ~13 environments, 300 Success rows covers about 3 to 5 weeks overall but **busy environments crowd out quiet ones** (a Production (Ankura) deploy from six weeks ago can fall off while QA churns). Return `window.oldest` and `window.truncated` so the UI can say "showing since 14 Sep". If board accuracy for prod matters, replace the single `LIMIT 300` with a per-environment window: `SELECT ... FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY environment ORDER BY started_at DESC) rn FROM deployments WHERE status ~* '(^|\s)success$') t WHERE rn <= 40`. Same index needs, bounded per env. Recommended for phase 3.
- **Index.** `deployments(status, started_at DESC)` helps A and the health query; only `idx_deployments_type` and `idx_deployments_fe_be` exist today. Add via the enrichment migration (section 4.4).
- **Jira key cap.** `jiraIssuesByKeys` does `slice(0, 100)`; 300 deployments commonly yield more than 100 distinct keys, so `/api/jira/deployed` silently drops the oldest. `jiraIssuesByKeysCached` chunks 100 at a time; with typical 150 to 250 keys that is 2 to 3 Jira calls on a cold cache.
- **Rate limits.** Concurrency is capped at 6 in-flight with one `Retry-After` retry (`jiraFetch`). Cold `/api/pipeline` = 2 to 3 search calls. Per-key memo (ttl 120 s) means different filter combinations share Jira results, so the lens homes (each calling `/api/pipeline` with different filters) do not multiply Jira load. In-process memo is per serverless instance, so expect an occasional cold fan-out after deploys; the 60 s `private` browser cache absorbs normal polling.
- **Regex cost.** `extractJiraKeys` over 300 rows x 6 text fields is trivial (sub-millisecond per row).
- **Response size.** 150 tickets x ~1 KB is about 150 KB; acceptable. Strip `notes` from the payload (only `runUrl`, versions, ids).

### 1.9 Tests

Unit (`lib/pipeline.ts`): env-name to column mapping for every observed name incl. unknown; placement for `furthest` vs `all`; a ticket in QA then Pre-Prod (stage skipped); state derivation order (Success then newer Failed -> `failed`; Failed then newer Success -> `deployed`; `Rerun - Success` counts); `hotfix`/`rolled_back`/`stuck`/`stage_mismatch` badges; `jira_keys` union with regex extraction; key case/dup normalisation.
Route: 401 without cookie; 401 with a wrong token; Bearer token accepted; `configured:false` path; Jira 500 degrades to DB-only; Jira 429 retried once; `assignee=me` unresolved -> 400; `limit` truncation flag; ETag round trip (second request with `If-None-Match` -> 304); `fresh=1` bypasses memo; 250 keys produce 3 Jira calls; filter clause is appended and quoted (injection string `"); DROP` ends up escaped by `jqlStr`).

### 2.3 Reuse

`isValidKey`, `jiraIssuesByKeysCached([key])` (the memo means a drawer click on a ticket already shown on the board costs zero Jira calls), `stageOf`, `jiraBrowseUrl`, the `loadDeployWindow`/`deploymentKeys`/`envMeta`/state-derivation code from `/api/pipeline` (single implementation, journey is a projection of the same per-env state), `/api/jira/release-notes` line format for `releaseNote`, `median`/lead-time maths from `insights` for `leadTimeToProdDays`.

### 2.4 SQL / JQL / GitHub

Do **not** limit to the 300-row window: an old ticket opened from search must still show its journey. Targeted, key-scoped query (key is already validated, passed as a parameter, never interpolated):

```sql
-- Phase 1..4 (before enrichment): word-bounded regex over the same text fields extractJiraKeys scans.
-- \y = word boundary in Postgres regex, so VID-12 does not match VID-123.
SELECT id, environment, status, deployment_type, branch, version, frontend_branch, backend_branch,
       frontend_version, backend_version, deployed_by, ticket_link, notes, started_at, completed_at, duration_seconds
FROM deployments
WHERE (COALESCE(notes,'') || ' ' || COALESCE(branch,'') || ' ' || COALESCE(version,'') || ' ' ||
       COALESCE(frontend_branch,'') || ' ' || COALESCE(backend_branch,'') || ' ' || COALESCE(ticket_link,'')) ~* $1
ORDER BY started_at DESC
LIMIT 50;
-- $1 = '\yVID-1234\y'

-- Phase 5 (after enrichment migration 4.4): index-backed, exact
WHERE jira_keys @> ARRAY[$1]::text[]
   OR (<regex above>)          -- keep the OR until legacy rows are backfilled
```

Full scan is acceptable at current table size (thousands of rows, one ticket click); the GIN index removes it after enrichment. Use `text_pattern`-safe escaping: the key passed `isValidKey` so it contains only `[A-Z0-9-]`; still bind as a parameter.

Jira: `key in (VID-1234)` (via the memoised helper). Optional extras behind `?expand=` later: `issuelinks`, `subtasks` (add to the `fields` list only for this route to avoid growing every list payload).

**Pull requests** (three sources, merged and de-duplicated by `repo#number`, each with `source`):
1. `deployments.prs` column once enrichment lands (`source: "deployment"`).
2. Parse legacy notes with `/\b(FE|BE)#(\d+)\b/g` (see the QA row in `app/api/migrate/route.ts`: `PR #FE#2640, BE#2710`). **Caveat:** these are the PRs of the whole *release*, not of this ticket. Use them only to label `shippedIn`, never to claim a PR belongs to the ticket.
3. GitHub search with the existing `GH_TOKEN`: `GET /search/issues?q=<KEY>+in:title,body+type:pr+repo:vidaisolutions/vidai-backend+repo:vidaisolutions/vidai-react&per_page=20` (`source: "github"`), cached 10 min per key. A PR belongs to the ticket when the key is in its title, body or head branch.
Then `shippedIn` = deployments whose `prs` (or parsed notes) include the PR number for the matching repo. This is what makes the journey exact for a PR even when the key is only on the PR.

### 2.5 Caching

`Cache-Control: private, max-age=60` + sha1 ETag. Server memo: issue 120 s (shared with pipeline), GitHub PR lookup 600 s, deployments not memoised (one cheap indexed query). `?fresh=1` clears both.

### 2.6 Auth

`canReadJira(session)` else 401 (same body as the Jira routes). Because deployment-only data is not secret but ticket titles are, return 401 uniformly.

| Case | Status | Body |
|------|--------|------|
| Invalid key format or foreign project | 400 | `{ error: 'Invalid ticket key', code: 'BAD_KEY' }` |
| Not authorised | 401 | `{ error: 'Admin login required' }` |
| Not in Jira **and** no deployments reference it | 404 | `{ error: 'Ticket not found', code: 'NOT_FOUND' }` |
| In deployments but Jira returns nothing (deleted, no permission) | 200 | `issue: null`, `jiraError` / `note: 'Not visible in Jira'`; journey still returned |
| Jira down / 429 after retry | 200 degrade | `issue: null`, `jiraError`; journey + deployments returned |
| GitHub token missing / rate-limited | 200 degrade | `pullRequests` from sources 1-2 only, `prsError: 'GitHub token not configured'` (message used by `/api/drift`) |
| DB error | 500 | `{ error }` |

### 2.8 Performance notes

A cold call is 1 DB query + 1 Jira search + 1 GitHub search; the three run in `Promise.all` with the DB result required but Jira/GitHub allowed to fail independently (`allSettled`). GitHub search is limited to 30 requests per minute per token and the same token backs `/api/drift` and `/api/compare`; the 10 min memo plus `prs=none` for hover previews protects it. Never call this endpoint per card on the board; the board already has the same data.

### 2.9 Tests

Unit: journey builder (skipped Stage, current vs done, failed after success, rollback, both prod columns pending); regex word boundary (`VID-12` must not match a row mentioning `VID-123`); legacy-note PR parser (`FE#2640`, `BE#2710`, mixed junk); `shippedIn` join; lead-time arithmetic.
Route: 400 for `vid-1`, `../x`, `VID-1;DROP`, foreign project; 404 when neither source knows the key; 200 with `issue: null` when only deployments exist; Jira 500 degrade; GitHub missing token degrade; `params` awaited (pass a `Promise`); ETag/304; unauthenticated 401; dedupe of a PR found by both deployment and GitHub.

## 3. `GET /api/me`

### 3.1 Request / response

`GET /api/me`, no params, **always HTTP 200** (anonymous is a valid state; the UI uses it to choose between login prompt and lens home).

```jsonc
// today (shared admin token, Option B / pre-SSO)
{ "authenticated": true, "email": null, "name": null, "role": "admin",
  "jiraAccountId": null, "authMode": "shared-token",
  "capabilities": { "readJira": true, "write": true, "settings": true } }

// anonymous
{ "authenticated": false, "email": null, "name": null, "role": "anonymous",
  "jiraAccountId": null, "authMode": "shared-token",
  "capabilities": { "readJira": false, "write": false, "settings": false } }

// after Option A (Google Workspace SSO)
{ "authenticated": true, "email": "asha.rao@vidaisolutions.example", "name": "Asha Rao", "role": "viewer",
  "jiraAccountId": "5b10a2844c20165700ede21g", "authMode": "sso",
  "capabilities": { "readJira": true, "write": false, "settings": false },
  "suggestedLens": "developer" }
```

`role`: `anonymous | viewer | admin`. This extends the existing `/api/auth/session` (`authenticated`, `role: 'admin'|'viewer'`); keep that route unchanged for backward compatibility and have it delegate to `getSession` later. Note `/api/auth/session` currently reports `viewer` for an unauthenticated visitor; `/api/me` introduces `anonymous` because under SSO a `viewer` is a *logged-in* read-only user. The UI should read `capabilities`, not compare role strings.

`suggestedLens` is optional (Option A only): from an env-configured map such as `LENS_BY_EMAIL` or Jira group; the client still lets the user switch and remembers the choice in `localStorage` / `?as=`.

### 3.2 Reuse and logic

- `getSession` wraps `isAdminRequest` (cookie `tracker_session` equals `ADMIN_TOKEN`, or `Authorization: Bearer`). Under shared-token auth there is no identity, so `email`/`jiraAccountId` are null and "my work" cannot work. That is exactly the Option B limitation in the proposal; the Pipeline/Tickets UI offers a person picker fed by `/api/jira/filters` `people[]` and passes the chosen `accountId` explicitly.
- Option A: Auth.js session -> `email`. Resolve `jiraAccountId` once via Jira `GET /rest/api/3/user/search?query=<email>` (via `jiraFetch`; needs "Browse users and groups" for the API token's account), take the entry whose `emailAddress` matches exactly (Jira hides emails by privacy setting; fall back to `displayName` match from `/api/jira/filters`, and if still unknown return `null`). Memoise 24 h with `cached('jira-user:'+email, 86400000, ...)`. Restrict to the `@vidaisolutions` domain server-side (`hd` claim plus email suffix check), never trust the client.
- No SQL.

### 3.3 Caching

`Cache-Control: private, no-store`, plus `Vary: Cookie`. Never ETag/304 (tiny and identity-dependent).

### 3.4 Errors

| Case | Status |
|------|--------|
| Not logged in | 200 `role: anonymous` |
| Jira lookup fails (Option A) | 200, `jiraAccountId: null`, `jiraLookup: 'failed'` (UI falls back to picker) |
| Unexpected exception | 500 `{ error }` |

### 3.5 Performance and security notes

Hot path, called on every page load: must not hit Jira on the request path after the first lookup. Do not return `ADMIN_TOKEN`, cookies or raw Auth.js tokens. Do not leave the `admin-change-me` default in production: `getSession` should treat an unset `ADMIN_TOKEN` as "no admin" outside development (today `lib/auth.ts` and `middleware.ts` both fall back to `'admin-change-me'`). Same applies to `WEBHOOK_SECRET` falling back to `change-me-in-production`.

### 3.6 Tests

Anonymous, admin cookie, admin Bearer, wrong cookie; `capabilities` matrix; no secret ever appears in JSON (assert response text does not contain the configured token); Option A: email domain rejection, Jira lookup memoised (one fetch for two calls), lookup failure degrades; header assertions (`no-store`).

## 4. Webhook enrichment (`POST /api/webhook`)

Goal from proposal: stop guessing ticket links from free text and make the journey exact.

### 4.1 Request additions (all optional, backward compatible)

| Field | Type | Notes |
|-------|------|-------|
| `jira_keys` | `string[]` | Keys the CI computed for this deployment (PR titles / commit messages between previous and new SHA). Normalised to upper case, validated with `isValidKey`, de-duplicated, max 100. Invalid items are dropped and reported in `warnings`. |
| `prs` | `{ repo: 'FE'\|'BE'\|'frontend'\|'backend'\|string, number: int, title?: string, sha?: string }[]` | Preferred form. Max 200. `FE`/`BE` normalise to `frontend`/`backend`. |
| `pr_number` | `int \| string` | Single-PR shorthand from the proposal, for workflows that deploy one PR. Treated as `prs: [{ repo: <component hint>, number }]`; repo taken from `frontend_branch`/`backend_branch`/`Component:` hint or `unknown`. |

Types wrong at the top level (e.g. `jira_keys` is a string) -> 400. Existing required fields unchanged (`environment`, `status`). Auth unchanged (`Authorization: Bearer $WEBHOOK_SECRET`; middleware skips this path).

Example (synthetic):

```json
{
  "environment": "QA", "status": "Success", "deployment_type": "standard",
  "frontend_branch": "qa", "backend_branch": "qa",
  "frontend_version": "v2.14.0-qa.31", "backend_version": "v2.14.0-qa.29",
  "ticket_link": "https://github.com/example-org/devops/actions/runs/111",
  "started_at": "2026-10-08T08:00:14Z", "completed_at": "2026-10-08T08:06:50Z",
  "jira_keys": ["VID-1234", "vid-1250"],
  "prs": [ { "repo": "BE", "number": 2710, "title": "VID-1234 fix MIS timezone" }, { "repo": "FE", "number": 2640 } ]
}
```

Response gains `warnings: string[]` (e.g. `"dropped invalid jira key 'FOO'"`); `deployment` now includes `jira_keys` and `prs`. Status stays 201.

### 4.2 Server behaviour

- Stored `jira_keys` = provided keys UNION `extractJiraKeys(notes, branch, version, frontend_branch, backend_branch, ticket_link)` at write time (so the column is complete and the GIN index covers legacy-style text too).
- Both INSERT statements in the route must be updated: the normal insert **and the rerun insert** (`ticket_link` already exists branch). Forgetting the rerun path would silently lose enrichment for reruns.
- The manual `POST /api/deployments` is not changed; it keeps regex-only linking (admin-entered rows).
- `notifyDeployment` unaffected.

### 4.3 CI side (outside this repo, documented here)

In the deploy workflow step that already builds the payload (`log-deployment-workflow.yaml`, `curl` to `TRACKER_WEBHOOK_URL`): compute keys and PRs from `git log <prev_deployed_sha>..<sha>` merge/squash subjects (`#1234` suffix is the PR number) with `grep -oE '[A-Z][A-Z0-9]{1,9}-[0-9]{1,6}'`, and add `jira_keys`/`prs` via `jq`. Keep them optional: a failure computing them must never fail the log step. Note the workflow currently builds JSON by string interpolation of inputs; use `jq -n --arg` for the new arrays to avoid quoting breakage.

### 4.4 Migration (idempotent; follow the `scripts/add-deployment-type.sql` precedent and/or the existing `POST /api/migrate`)

```sql
ALTER TABLE deployments
  ADD COLUMN IF NOT EXISTS jira_keys TEXT[] NOT NULL DEFAULT '{}',
  ADD COLUMN IF NOT EXISTS prs       JSONB  NOT NULL DEFAULT '[]';
CREATE INDEX IF NOT EXISTS idx_deployments_jira_keys ON deployments USING GIN (jira_keys);
CREATE INDEX IF NOT EXISTS idx_deployments_status_started ON deployments (status, started_at DESC);
CREATE INDEX IF NOT EXISTS idx_deployments_env_started ON deployments (environment, started_at DESC);
```

Constant `DEFAULT` on PG 11+ is metadata-only (no table rewrite). **Deviation from the proposal:** section 8 says "no DB table changes for phases 1-3", which still holds; this migration belongs to phase 5 only. It also uses `prs JSONB` instead of a scalar `pr_number` because a deployment ships many PRs (the QA row in `migrate/route.ts` lists 15). A scalar `pr_number` column would be lossy.
Backfill (optional script like `scripts/fix-imported-actors.js`): for each row set `jira_keys = extractJiraKeys(...)` and `prs` parsed from `FE#nnn`/`BE#nnn` in notes; run once, safe to re-run.
Rollout order: deploy migration -> deploy app reading with `COALESCE`/UNION (works with and without data) -> update CI -> backfill. Reads must tolerate the column being absent only if migration is guaranteed first; simplest is to ship the migration one release earlier.

### 4.5 Errors

| Case | Status |
|------|--------|
| Bad token | 401 (unchanged) |
| Missing `environment`/`status` | 400 (unchanged) |
| `jira_keys`/`prs` wrong top-level type, or `prs` > 200 / `jira_keys` > 100 | 400 `{ error, field }` |
| Individual malformed item | dropped + `warnings` entry, still 201 |
| Insert fails (e.g. migration not run) | 500 (existing handler) |

### 4.6 Performance and security notes

Adds two small columns to a row that is already written once; the cost is negligible. Validate before interpolating anything: keys go through `isValidKey`, PR numbers through `Number.isInteger`, repo through an allow-list, all passed as bound parameters (`$n`), never concatenated. Cap payload sizes (Next's default body limit is generous; enforce counts above). Do not log the full body (contains no secrets but is noisy).

### 4.7 Tests

Normalisation (`vid-1250` -> `VID-1250`, dupes, invalid `FOO`, project not in `JIRA_PROJECTS`); `FE`/`BE` mapping; `pr_number` shorthand; union with regex-extracted keys; both insert paths (normal and rerun with an existing `ticket_link`) persist the new columns; legacy payload without new fields still 201 with `{}`/`[]`; wrong types -> 400; `warnings` returned; bad token 401 with no DB call.

## 6. Implementation order and risks

1. `lib/auth.ts` `getSession`/`canReadJira`; `GET /api/me`. (Unblocks lens defaults; no data risk.)
2. `lib/jira.ts` additive: `assigneeId`, `jiraIssuesByKeysCached`; `lib/pipeline.ts` pure logic with unit tests first.
3. `GET /api/pipeline`, then `GET /api/tickets/[key]` (DB regex path; GitHub PRs behind `prs=live`).
4. Migration + webhook enrichment + CI payload + backfill (phase 5); flip `/api/tickets/[key]` to the GIN query.

Risks and watch-outs:
- Behaviour change in the shared success window (`Rerun - Success`) affects `/api/jira/deployed` and `insights` ready-to-ship; ship with a note and a test.
- In-process memo is per serverless instance; do not rely on it for correctness, only cost.
- Per-env window (1.8) changes which tickets show for rarely deployed prod environments; decide before the board ships.
- `app/api/deployments/[id]/route.ts` PATCH builds `SET` clauses from request-body keys (`${field} = $n`), which is an SQL-injection vector for any admin-token holder; unrelated to this spec but worth a separate fix before more write surface is added.
- `app/api/migrate` `GET` mutates data and contains hard-coded inserts; do not extend it, put new DDL in `scripts/` and run once.
